# FABRIC (r01f) security component of an OGOV system

Every OGOV system has one **security** component shared by all its sub-systems (components): `{domain bai}-ogov-{system id}-security-api` and `…-security-core`. Unlike a regular component, its contents don't depend on the system: it always has the same model objects, service interfaces, entities, DAOs and services. Only the identifiers change (system id, app codes, BAI). That's why it is generated by **copying a template**, not by writing classes one by one: a script copies the template byte by byte and replaces the identifiers, so the result is exactly what a hand-maintained security component looks like (same formatting, line endings and comments).

## The template

`presencia-web/ogov-pocs/ogov-samplesys/` (relative to the workspace root, the folder that contains `admindigital-common` and `presencia-web`):

| Project | Maven parent | Modules |
| :--- | :--- | :--- |
| `bai-ogov-samplesys-security-api` | `ogov.samplesys.security.api:ogovSampleSysSecurityAPI` | `…APIModelClasses`, `…APIClasses`, `…APIBootstrapGuiceClasses`, `…APIBootstrapSpringClasses` |
| `bai-ogov-samplesys-security-core` | `ogov.samplesys.security.core:ogovSampleSysSecurityCORE` | `…COREDBPersistenceClasses`, `…COREBootstrapGuiceClasses`, `…COREBootstrapSpringClasses` |

Only `pom.xml`, `README.md` and `src/**` are part of the template; the script never copies IDE, build or git files (`.project`, `.classpath`, `.settings/`, `target/`, `bin/`, `.git*`, `.gitlab-ci.yml`).

The **test template** lives in the domain test project `ogov-test/e80a180-ogov-test/`, next to the other components' tests:

| Module | Template files (package `ogov.samplesys.security.test…`) |
| :--- | :--- |
| `ogovTestCommonClasses` (`src/main/java`, `.test.persistence`) | `OG99SecurityScenarios` (the acceptance scenarios, written once), `OG99SecurityTestDataLoader` (idempotent demo data: principals, logins, resources, auths), `OG99SecurityContextProviderForTest`, `OG99HibernateAssertionsWorkaround` |
| `ogovTestGuiceClasses` (`src/test/java`, `.test.guice.persistence`) | `OG99TestGuiceForSecurityBase`, `OG99TestGuiceForSecurityPersistableObjects` |
| `ogovTestSpringClasses` (`src/test/java`, `.test.spring.persistence`) | `OG99TestSpringBootstrapForSecurity`, `OG99TestSpringForSecurityPersistenceBase`, `OG99TestSpringForSecurityPersistableObjects` |
| `ogovTestSpringClasses` (`src/test/resources/config/default`) | `samplesys-security-database.yml` (the `db.security.*` Spring properties) |

plus the samplesys security **registration blocks** the script copies for the new system: the `ogov.samplesys.security.{api,core}.version` properties in the parent `pom.xml`, the `SampleSys / Security` dependency block in each module `pom.xml`, the `samplesys-security-database.yml` import in `ogovTestSpringClasses/src/test/resources/application.yml`, and the Guice config component `og91/components/og91.security.dbpersistence.xml` in `ogov-config/e80a180-ogov-config/ogovCOREConfig/src/main/config`.

The script replaces these tokens (and nothing else):

| Token in the template | Becomes | Example (communic) |
| :--- | :--- | :--- |
| `samplesys` / `SampleSys` / `SAMPLESYS` | system id in packages and folders / Maven artifacts and pom names / constants (`OG00AppCodes.SAMPLESYS_*`, `SAMPLESYS_SECURITY_*`) | `communic` / `Communic` / `COMMUNIC` |
| `OG90` / `og90` | API app code | `OG10` / `og10` |
| `OG91` / `og91` | CORE app code (classes, tables `OG91SECURITY…`, persistence unit, config files) | `OG11` / `og11` |
| `bai` (whole word) | domain BAI, the repo folder prefix | `e80a177` |
| `(samplecomp and the ones to come)` in the READMEs, `(samplecomp...)` in `OG90AppCodesForSecurity` | the system's other components | `(media-register and the ones to come)`, `(media register...)` |

A replaced name can be longer or shorter than in the template (`samplesys` → `communic`), which would break the house alignment of what is aligned under it (parameters under the first one, chains…). So the script re-aligns the substituted Java lines with the `r01-java-formatter` skill's formatter (only spaces change) and prints `re-aligned: …` for each file it touched. Don't format the generated files again.

## How to work

### 1. Gather the inputs

- **Given:** the `{system id}` (lowercase, e.g. `communic`). The user may also give the domain BAI, the app codes or the PascalCase of the system.
- **Detected by the script** when not given:
  - API / CORE app codes: from `{SYSTEM}_API_APPCODE_STR` / `{SYSTEM}_CORE_APPCODE_STR` in `OG00AppCodes` (`ogov-common/e80a180-ogov-common-api/ogovCommonAPIClasses/src/main/java/ogov/common/api/OG00AppCodes.java`).
  - Domain BAI: the prefix of the system's existing projects in `ogov-pocs/ogov-{system id}/` (e.g. `e80a177-ogov-communic-media-register-api` → `e80a177`).
  - PascalCase (`SampleSys`, `Communic`): from the `artifactId` of an existing component pom of the system; otherwise the id capitalized. Pass `--system-pascal` for multi-word ids whose casing can't be guessed.
  - Components named in the README / javadoc: the system's existing components other than `security`.
- **Prerequisite: the system must be registered in `OG00AppCodes`** (`{SYSTEM}_STR`, `{SYSTEM}_API_APPCODE_STR` / `_API_APPCODE`, `{SYSTEM}_CORE_APPCODE_STR` / `_CORE_APPCODE`), because the generated `{apiAppCode}AppCodesForSecurity` and bootstrap classes reference those constants. If the script can't find the app codes, the system isn't registered: ask the user for the codes (propose the next free pair, API even `OGx0`, CORE odd `OGx1`; a code is taken if it appears anywhere in the workspace sources, not only in `OG00AppCodes`, e.g. `OG20`/`OG21` in `OG00CommonAppCodes`) and register them following the `r01-architecture` skill (task 1, step 1.1) before generating.
- If the system folder doesn't exist and no BAI is given, ask for the BAI rather than guessing.

### 2. Dry run, then generate

Run the bundled script from the workspace (paths relative to this skill's folder):

```bash
python scripts/generate_security.py --system <system id> --with-tests --dry-run
python scripts/generate_security.py --system <system id> --with-tests
```

- Without `--with-tests` only the `-api` / `-core` projects are generated. Generate the tests too unless the user asked only for the API / CORE, and say so in the report.
- `--only tests` generates just the tests, config and registrations (the `-api` / `-core` already exist); `--only api|core` just one project.
- Other optional arguments: `--domain-bai`, `--api-app-code`, `--core-app-code`, `--system-pascal`, `--components a,b`, `--out-root <dir>` (generate the projects elsewhere, e.g. to compare), `--tests-root <ogov-test project>`, `--config-root <ogovCOREConfig/src/main/config>`, `--workspace <root>`, `--no-format`, `--force`.

Check the first line of the output (`system=… bai=… api=… core=… components=…`): those are the values that went into every file. Then read each section:

- **`[api]` / `[core]`**: the script refuses to overwrite an existing `-security-api` / `-security-core` folder; if one exists, tell the user and only use `--force` if they say so (it deletes the folder first, including any hand-made changes in it).
- **`[tests]`**: the test files (package `ogov.{system id}.security.test…` and `{system id}-security-database.yml`). Existing ones are not overwritten without `--force`.
- **`[config]`**: the Guice config component `{core}/components/{core}.security.dbpersistence.xml`, which points to `{core}/{core}.dbpersistence.properties.xml`. It is only written when that properties file exists. If the script says `PENDING`, the system has no CORE DB config in `ogov-config` yet: the Guice tests won't start until it exists. Tell the user; don't invent DB settings (mirror `og91/og91.dbpersistence.properties.xml` and its `ogov-config-byenv` overlay only if they ask).
- **`[registrations]`**: each file says `registered`, `already registered` (nothing to do) or `ERROR` (the template block wasn't found: register it by hand following the samplesys one). Registrations are inserted right after the samplesys security blocks, so running the script twice changes nothing.

### 3. Register what the runtime looks up

The script doesn't touch `OG00AppCodes`. Do this yourself, or list it for the user if it's out of scope:

- **Model package** in `OG00AppCodes.MODEL_JAVA_PACKAGES`: add `JavaPackage.named("ogov.{system id}.security.api.model")` next to the existing ones (the marshaller ignores model classes in unregistered packages). Apply `r01-java-formatter` to the changed lines (see `AGENTS.md`).
- **Spring DB properties**: the generated `{system id}-security-database.yml` holds the local `db.security.*` settings (the key is the core module, `security`, the same for every system). Other Spring hosts need their own.
- **Other hosts** that should load the component need its Maven dependencies (`…COREBootstrapGuiceClasses` / `…COREBootstrapSpringClasses`).

### 4. Report back

- The two folders created, their Maven parents and the number of files; the test files and the registrations (`registered` / `already registered`).
- The values used (and which ones were detected vs. given).
- What is still pending (`PENDING` config, `OG00AppCodes`).
- Don't run the tests unless asked: they are integration tests against the real database and need the AspectJ agent.
- Which Eclipse projects to refresh (F5 + Maven update), since the files were written outside the IDE: the new `-api` / `-core` projects (import them), `ogovTestCommonClasses`, `ogovTestGuiceClasses`, `ogovTestSpringClasses` and `ogovCOREConfig`. Or build with `mvn -Pbatsdlc clean install` (the versions in `pom.xml` are placeholders such as `OGOV-{SYSTEM}-SECURITY-API-VERSION`).

## Changing the template

The template **is** the source of truth for every system's security component. To change what gets generated, edit the samplesys security files (the projects under `ogov-samplesys/bai-ogov-samplesys-security-*`, the `ogov.samplesys.security.test` tests, their registration blocks and `og91.security.dbpersistence.xml`) and keep them a valid, house-formatted samplesys project:

- Write identifiers with the template tokens (`samplesys`, `SampleSys`, `SAMPLESYS`, `OG90`, `og90`, `OG91`, `og91`, `bai`), so they are replaced. Avoid those strings where they must **not** be replaced (e.g. a word `bai` in prose).
- Keep only `pom.xml`, `README.md` and `src/**` in the projects.
- Keep the shape of the registration blocks (the script finds them with a regex): the two `ogov.samplesys.security.{api,core}.version` lines, the `<!-- SampleSys / Security -->` box comment followed by one `<dependency>`, and the `samplesys-security-database.yml` import line.
- After changing it, run the regression check. It regenerates the security component and tests of a system that already has them (communic) in a temp folder and compares them byte by byte with the real ones, without modifying the workspace:

```bash
python scripts/validate_roundtrip.py
```

It must end with `RESULT: IDENTICAL`; otherwise it lists the missing, extra and different files with a short diff (`compare_trees.py`, which you can also run on two folders yourself). If the reference system's app codes are no longer in `OG00AppCodes`, pass them: `--api-app-code OG10 --core-app-code OG11`.

## What the security component contains

For questions about where a security class lives (`{api}` / `{core}` = app codes, packages under `ogov.{system id}.security`):

| Layer | Package | Types |
| :--- | :--- | :--- |
| API model | `.api.model`, `.api.model.authorization` | `{api}SecurityPrincipalForPerson` (extends `OG00SecurityPrincipalForPerson`), `{api}SecurityRoles`, `{api}AuthorizationResourcesData` |
| API | `.api` | `{api}AppCodesForSecurity` (`{SYSTEM}_SECURITY_*` constants: module, API/CORE FQN, db persistence component, secured app code), `{api}ClientAPIForSecurity` |
| API interfaces | `.api.interfaces[.{object}]` | `{api}IsServiceInterfaceForSecurity`; CRUD/Find(/Count) services for `SecurityPrincipal`, `Login`, `LoginEntry`, `AuthorizationTargetResource`, `AuthorizationOnResource`; `{api}UserPasswordLoginServices` |
| API sub-apis | `.api.{object}` | `{api}SecurityPrincipalSubApi`, `{api}LoginSubApi`, `{api}LoginEntrySubApi`, `{api}AuthorizationTargetResourceSubApi`, `{api}AuthOnResourceSubApi` and their `{api}ClientAPIDelegateFor…` |
| API bootstrap | `.api.bootstrap.{guice,spring}` | `{api}APIBootstrapGuiceModuleForSecurity`, `{api}APISpringBootstrapConfigurationForSecurity` |
| CORE entities | `.core.db.entities[.{object}]` | `{core}IsDBEntityForSecurity`, `{core}DBEntityFor{Object}` (tables `{core}SECURITYPRINCIPAL`, `…LOGIN`, `…LOGINENTRY`, `…AUTHRESOURCE`, `…AUTHONRESOURCE`) + `META-INF/jpa/{core lower}.security.persistence.xml`, `META-INF/persistence.xml` |
| CORE DAOs | `.core.db.dao.{object}` | `{core}DB{CRUD,Find,Count}For{Object}` |
| CORE services | `.core.db.services[.delegates].{object}` | `{core}IsCOREPersistenceServiceForSecurity`, `{core}CORE{CRUD,Find,Count}ServicesFor{Object}` and `…ServicesDelegateFor{Object}`, `{core}COREUserPasswordLoginServices[Delegate]` |
| CORE bootstrap | `.core.bootstrap.{guice,spring}` | `{core}COREBootstrapGuiceConfigBuilderForSecurity`, `{core}COREPersistenceBootstrapGuiceModuleForSecurity`, `{core}CORESpringBootstrapConfigurationForSecurity`, `{core}CORESpringCoreBootstrapPersistenceModulePostProcessorForSecurity` |

The common security layer (security contexts, providers, `OG00SecurityPrincipalForPerson`) lives in `ogov-common`; this component only specializes it per system.
